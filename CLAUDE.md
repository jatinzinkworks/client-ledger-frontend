# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The **Client Ledger** frontend: one **pnpm + Turborepo monorepo** holding a **web app** and a **mobile app** that share their API client, validation rules and design tokens. The backend is the sibling Spring Boot service in `../client-ledger-backend` (base path `/psc/cl/v1`, OpenAPI at `/v3/api-docs`). Design mocks and the Zinkworks design system live in `../mock`.

```
apps/
  web/       Vite + React 19 + Tailwind v4 + shadcn/ui + react-router 7   (@cl/web)
  mobile/    Expo SDK 57 + expo-router + NativeWind 4 (Tailwind v3)       (@cl/mobile)
packages/
  api/       orval-generated TanStack Query hooks, types and zod schemas + fetch client  (@cl/api)
  schemas/   zod form schemas shared by both apps (cross-field rules, defaults, labels) (@cl/schemas)
  tokens/    Zinkworks design tokens → web theme.css and the NativeWind preset          (@cl/tokens)
```

## Commands (run from the repo root)

- `pnpm install` — install everything (pnpm 12, Node ≥ 22)
- `pnpm dev` / `pnpm dev:web` — Vite dev server for the web app (http://localhost:5173)
- `pnpm dev:mobile` — `expo start` for the mobile app (press `a` / `i` / `w`, or scan with Expo Go)
- `pnpm dev:mobile:usb` — Android phone over USB: `adb reverse` for 8081/8080, then Expo with the API pointed at `localhost:8080` (no Wi-Fi/firewall needed). `--no-start` only re-applies the reverse routes after re-plugging. Script: [apps/mobile/scripts/usb.mjs](apps/mobile/scripts/usb.mjs)
- `pnpm build` · `pnpm typecheck` · `pnpm lint` — Turborepo across all workspaces
- `pnpm test` — Vitest across the workspaces that have tests
- `pnpm api:fetch-spec` — refresh `packages/api/openapi.json` from a running backend (`API_SPEC_URL` overrides `http://localhost:8080/v3/api-docs`)
- `pnpm api:generate` — regenerate `packages/api/src/generated/` from that snapshot
- `pnpm --filter @cl/tokens generate` — regenerate `packages/tokens/theme.css` after editing tokens
- `pnpm --filter @cl/mobile doctor` — `expo-doctor` (SDK / dependency compatibility)
- Scope any script to one workspace with `pnpm --filter <name> <script>`, e.g. `pnpm --filter @cl/web test:watch`.

**DO NOT RUN THE TESTS until asked.** Keep writing and updating tests alongside the code as normal, but do not run `pnpm test`, `test:watch` or `test:coverage` on your own initiative — wait for an explicit request. (`pnpm build` / `pnpm typecheck` type-check the test files, which is not the same as running them.)

Tests use [Vitest](https://vitest.dev); the web app adds React Testing Library (jsdom, setup in [apps/web/src/test/setup.ts](apps/web/src/test/setup.ts)). Tests are co-located as `*.test.ts(x)`. Prefer testing pure logic in `packages/` directly; for components, assert on behaviour (labels, roles, submitted values) rather than implementation details. The mobile app has no test runner yet.

## Environment

- **Web** ([apps/web/.env](apps/web/.env)): `VITE_API_BASE_URL` is empty by default, so the browser calls its own origin and the Vite dev server **proxies `/psc` to `VITE_DEV_PROXY_TARGET`** (`http://localhost:8080`). The backend sends no CORS headers, so calling `:8080` directly from the browser fails — only set a full URL for a backend that allows the origin. In production, serve the app and the API from the same origin. `VITE_LOGOUT_URL` / `VITE_IDP_LOGOUT_URL` are reserved for IAP / Entra sign-out (not wired up yet; the IAP URL must be fetched with `redirect: 'manual'`). Vite inlines env at start-up — **restart the dev server after editing `.env`**.
- **Mobile** ([apps/mobile/.env](apps/mobile/.env)): `EXPO_PUBLIC_API_BASE_URL` is the backend as seen *from the device* — `localhost` on the iOS simulator, `10.0.2.2` on the Android emulator, the machine's LAN IP on a physical device. Native apps are not subject to CORS. Restart `expo start` after editing.

## Docker (web app)

[Dockerfile](Dockerfile) builds **only the web app**: it installs `@cl/web` and its workspace packages (`pnpm install --filter "@cl/web..."`, so Expo stays out), runs their unit tests, builds, and serves `apps/web/dist` from non-root nginx on port 8080. The bundle is built with `VITE_API_BASE_URL` empty, and nginx proxies `/psc/` to **`API_UPSTREAM`**, a runtime env var holding the backend origin, e.g. `docker run -e API_UPSTREAM=https://<backend> -p 8080:8080 <image>`. The proxy keeps the API same-origin, since the backend sends no CORS headers. [docker-entrypoint.sh](docker-entrypoint.sh) renders [nginx.conf.template](nginx.conf.template) and refuses to start without `API_UPSTREAM`. When adding a workspace package, add its `package.json` to the manifest `COPY` lines in the deps stage. `deploy.sh` / `deploy-dev.sh` set `API_UPSTREAM` on the Cloud Run service. They look it up from `BACKEND_SERVICE` in [variables.sh](variables.sh) via `gcloud`; an `API_UPSTREAM` already in your shell overrides the lookup. Don't pass `VITE_API_BASE_URL` to these builds.

## Architecture

### Shared packages — the reason this is a monorepo

- **`@cl/api`** — everything under `src/generated/` is produced by **orval** from the committed [openapi.json](packages/api/openapi.json) snapshot: typed request/response models, TanStack Query hooks (`useGetPaymentTerms`, `useSavePaymentTerms`, …) and zod schemas (`@cl/api/zod`). **Never edit generated files** — change the backend, `pnpm api:fetch-spec`, `pnpm api:generate`. All requests go through the mutator [fetcher.ts](packages/api/src/fetcher.ts): each app calls `configureApi({ baseUrl, … })` once at start-up; non-2xx responses throw `ApiError` carrying the backend's `ErrorResponse` (`errorMessage` / `fieldErrors` / `isNotFound` in [errors.ts](packages/api/src/errors.ts)). Hand-written hooks that compose the generated ones for a screen (e.g. [usePaymentTerms](packages/api/src/hooks/usePaymentTerms.ts)) live in `src/hooks/` so both apps share screen logic.
- **`@cl/schemas`** — zod **form** schemas. Field bounds and defaults are imported from the generated zod so they track the backend; cross-field rules the spec cannot express (the backend's `@AssertTrue` checks) are added here — **keep the rules identical to the Java side**, but word the messages for users (Title Case, like the mocks). Also holds the request mappers (`toPaymentTermsRequest`), form defaults and field labels/hints — both apps render the same copy. Forms use react-hook-form + `zodResolver` in both apps.
- **`@cl/tokens`** — the single source for the Zinkworks palette, semantic light/dark colours (shadcn names: `background`, `card`, `muted-foreground`, `border`, …), radius and fonts in [src/index.js](packages/tokens/src/index.js). Web imports the generated [theme.css](packages/tokens/theme.css); mobile uses [tailwind-preset.cjs](packages/tokens/src/tailwind-preset.cjs) plus NativeWind `vars()` in [ThemeRoot](apps/mobile/src/theme/ThemeRoot.tsx). So `bg-card` / `text-muted-foreground` mean the same in both apps. Edit `src/index.js`, then regenerate `theme.css` (a test fails if they drift).
- Shared packages are consumed **as TypeScript source** (no build step); `main`/`exports` point at `src/`.

### One React

`react`, `react-dom`, `@types/react`, `typescript`, `zod`, `@tanstack/react-query` and `vitest` versions come from the **`catalog:`** in [pnpm-workspace.yaml](pnpm-workspace.yaml) — reference them as `"catalog:"`, never a literal range. React must be a single copy repo-wide (the shared hooks run inside both apps) and **Expo dictates the version**, so the web app follows it; bump it only as part of an Expo SDK upgrade. This is why the web app is on react-router 7 (v8 requires a newer React than Expo ships). The web Vite config also `dedupe`s React and React Query.

### Web app ([apps/web](apps/web))

- [src/main.tsx](apps/web/src/main.tsx) — `configureApi`, `QueryClientProvider`, `ThemeProvider`, `BrowserRouter`; [src/App.tsx](apps/web/src/App.tsx) — route table; [AppLayout](apps/web/src/components/AppLayout.tsx) — sidebar shell driven by [utils/navigation.ts](apps/web/src/utils/navigation.ts).
- Pages fill the width beside the sidebar — no centred max-width wrapper. Card grids use `grid-cols-[repeat(auto-fill,minmax(min(100%,320px),1fr))]` so wide screens get more columns.
- `src/pages/` route screens · `src/components/` reusable blocks (`ui/` = shadcn primitives, `settings/`, …) · `src/theme/` light/dark · `src/utils/` config and constants · `src/lib/utils.ts` = `cn`.

### Mobile app ([apps/mobile](apps/mobile))

- Expo Router: every file in `src/app/` is a route; `_layout.tsx` files are navigators. [src/app/_layout.tsx](apps/mobile/src/app/_layout.tsx) — `configureApi`, `QueryClientProvider`, `ThemeRoot`; `(tabs)/` — bottom tabs driven by [utils/navigation.ts](apps/mobile/src/utils/navigation.ts). Keep non-route code out of `src/app/`.
- Catalogs on mobile (Services, Managers): the list is a `(tabs)/` tab; create / edit are full-screen routes (`service/new`, `service/[id]`, `manager/new`, `manager/[id]`) pushed over the tabs, reading the record from the cached list. Bind form fields with `TextControl` / `SelectControl` from [FormControls](apps/mobile/src/components/ui/FormControls.tsx). Typed routes are on — after adding a route, run `expo start` once so `.expo/types` picks it up (`expo export` does not).
- NativeWind cannot apply opacity modifiers (`bg-brand/10`) to the token colours, because they are CSS variables holding hex values — use borders or solid fills on mobile.
- Settings on mobile is one [SettingsCard](apps/mobile/src/components/settings/SettingsCard.tsx) per section, each with its own form and Save button, fed by the same `@cl/api` hook and `@cl/schemas` schema as the web section.
- `src/components/ui/` is the small native UI kit (Button, Card, DaysField, TextField, SelectField — a bottom-sheet picker, since React Native has no <select>) styled with NativeWind classes; `src/theme/` maps tokens onto CSS variables and the navigation theme; the app follows the OS appearance.
- **Read [apps/mobile/AGENTS.md](apps/mobile/AGENTS.md) before touching Expo APIs** — Expo changes every SDK; check the versioned docs, and add native packages with `npx expo install <pkg>` (run in `apps/mobile`), not `pnpm add`, so versions match the SDK. `ios/` and `android/` are generated (CNG) and git-ignored — configure native behaviour in `app.json`.
- pnpm isolates dependencies, so anything injected into app code by a build tool must be a **direct** dependency of `@cl/mobile` (that's why `react-native-css-interop` and `babel-preset-expo` are listed explicitly). Metro's monorepo support is automatic — don't add `watchFolders` / `nodeModulesPaths`.

### Backend contract notes

- API paths are versioned under `/psc/cl/v1`. **URL-encode path params** (`encodeURIComponent`) in hand-built paths and route links. orval does **not** encode them in generated URLs, so the hand-written hooks encode ids before calling generated mutations (see [useServiceCatalog](packages/api/src/hooks/useServiceCatalog.ts)).
- Global Settings resources (payment terms, firm details) are singletons: `GET` returns 404 until first saved (treat as "not configured" and show defaults), `POST` creates (201) or replaces wholesale (200) — send every field, and **omit** blank optional strings rather than sending `""` (the backend's `@Pattern` rejects empty strings). Wrap each in a hook built on [singletonSetting](packages/api/src/hooks/singletonSetting.ts).
- On the web Settings screen each section is **its own react-hook-form form** ([SettingsForm](apps/web/src/components/settings/SettingsForm.tsx)) so an unconfigured section never blocks saving another; the header Save validates all changed sections, then saves only those. Add a new section by adding its schema in `@cl/schemas`, a hook in `@cl/api`, a `*Section` component, and wiring it into `SettingsForm`.
- **Service catalog** (`/psc/cl/v1/services`, web [ServicesPage](apps/web/src/pages/ServicesPage.tsx)): a plain list + CRUD, wrapped by [useServiceCatalog](packages/api/src/hooks/useServiceCatalog.ts) (mutations invalidate the list). The invoice schedule must match the billing frequency — [services.ts](packages/schemas/src/services.ts) holds those rules, the per-frequency request mapping, the card schedule text and the next-invoice calculation. Name clashes return 409 and are shown on the name field; deleting a service companies use returns 409.
- **Manager catalog** (`/psc/cl/v1/managers`, web [ManagersPage](apps/web/src/pages/ManagersPage.tsx)): the same list + CRUD shape, wrapped by [useManagerCatalog](packages/api/src/hooks/useManagerCatalog.ts), which sorts the list by full name (the backend orders by last name); rules, labels and display helpers in [managers.ts](packages/schemas/src/managers.ts). Every field is mandatory; a duplicate email returns 409 and is shown on the email field. The table's columns are an array in [ManagersTable](apps/web/src/components/managers/ManagersTable.tsx); Clients comes from `clientCount` (also shown in Edit Manager via `managerClientsLabel`) — add Monthly Salary / Pending there when the API carries them.
- **Clients** (`/psc/cl/v1/clients`, web [ClientsPage](apps/web/src/pages/ClientsPage.tsx)): the list returns `ClientSummaryResponse` (company **names** only); fetch a client by id for full companies. Wrapped by [useClients](packages/api/src/hooks/useClients.ts) (sorted by full name; list + create so far); the list filters by search text and manager (`filterClients`). A card links to `/clients/:id` ([ClientDetailPage](apps/web/src/pages/ClientDetailPage.tsx)), loaded by [useClient](packages/api/src/hooks/useClient.ts) (404 → "Client Not Found", no retries). A company row links to `/clients/:id/companies/:companyId` ([CompanyDetailPage](apps/web/src/pages/CompanyDetailPage.tsx)), loaded by [useCompany](packages/api/src/hooks/useCompany.ts): the company plus its assigned services (`listServices_1`). Build detail-page links with [utils/routes.ts](apps/web/src/utils/routes.ts) (it encodes ids). API dates (`2026-10-15`) go through `formatApiDate` so they don't shift a day. Web list tables use [DataTable](apps/web/src/components/DataTable.tsx) (a column array); detail pages use [PageBreadcrumb](apps/web/src/components/PageBreadcrumb.tsx) and [DetailHeader](apps/web/src/components/DetailHeader.tsx). [clients.ts](packages/schemas/src/clients.ts) holds the onboarding rules: every field mandatory, at least one company (a `useFieldArray` on web), manager must exist (create returns 404 otherwise — shown on the manager field). Backend field errors on companies arrive as `companies[0].address`; `clientFieldFromApi` turns them into react-hook-form paths. The client discount is optional (blank is omitted and the backend stores 0). Each company block also has an optional discount: blank is omitted (`toCompanyRequest`), so the company takes the client's. Onboard Client stays disabled until `isClientFormComplete` says every mandatory field is filled. Shared field builders (`requiredText`, `requiredEmail`, `requiredPhone`) live in [fields.ts](packages/schemas/src/fields.ts).
- **Edit Client** ([EditClientForm](apps/web/src/components/clients/EditClientForm.tsx), `PUT /clients/{id}` via `useClient().update`): sends the client's own fields only (`toClientUpdateRequest`); companies are untouched and keep their discounts, and only companies added later take the client's (`EDIT_DISCOUNT_HINT`). **Delete Client** sits in the Edit Client footer ([DeleteButton](apps/web/src/components/DeleteButton.tsx) with `deleteClientWarning`); the backend deletes the companies too and returns 409 while any company has services (`DELETE_CLIENT_IN_USE`, via the button's `conflictMessage`). After deleting, the page navigates to `/clients`. The client's own fields are one shared block, [ClientDetailsFields](apps/web/src/components/clients/ClientDetailsFields.tsx), used by both Onboard and Edit.
- **Companies of a client**: Add Company ([AddCompanyForm](apps/web/src/components/clients/AddCompanyForm.tsx), `POST /clients/{id}/companies`) and Edit Company on the company page ([EditCompanyForm](apps/web/src/components/clients/EditCompanyForm.tsx), `PUT /clients/{id}/companies/{companyId}` via `useCompany().update`) are both thin wrappers over [CompanyForm](apps/web/src/components/clients/CompanyForm.tsx) (Edit also carries Delete Company in its footer, via `footerStart`; after deleting, the page goes back to the client): one company, held as a one-item `companies` array so it reuses [CompanyFields](apps/web/src/components/clients/CompanyFields.tsx). An omitted discount becomes the client's on both, so Edit shows the stored discount even when it is 0 (`companyFormDefaults`). At most 50 per client (`companiesLeft`, 409 → `TOO_MANY_COMPANIES`). The client page's companies come from `GET /clients/{id}/companies` (`useClient().companies`), the only response carrying each company's `serviceCount` (shown in a Services column); company and service mutations invalidate that list. Delete is a trash icon per row in [CompaniesTable](apps/web/src/components/clients/CompaniesTable.tsx), disabled for the only company and for one with services (the backend refuses both, 409 → `LAST_COMPANY_REASON` / `DELETE_COMPANY_IN_USE`). The icon's cell stops click propagation, because React events bubble out of the dialog portal to the clickable row. Onboard Client uses the multi-company list, [CompanyListFields](apps/web/src/components/clients/CompanyListFields.tsx). `useClient` exposes `addCompany` / `deleteCompany` and refreshes the client and the list.
- **Services of a company** (`/clients/{clientId}/companies/{companyId}/services`, tag Client Services): Add Service on the company page ([AddServiceForm](apps/web/src/components/clients/AddServiceForm.tsx), `POST` via `useCompany().addService`, which refreshes the company's services and the catalog's usage counts). The request carries only the catalog service, delivery date, optional discount and optional note — the **fee is not sent**: it is the catalog's standard fee, shown as a hint and in [ChargeSummary](apps/web/src/components/clients/ChargeSummary.tsx) (net charge, GST at the service's `gstRatePercent` and the total with GST, all from `chargeBreakdown`; the services table shows the same Net Charge / GST / Total) and [DueSchedule](apps/web/src/components/clients/DueSchedule.tsx) (the total with GST for each of the next 5 due dates from the delivery date via `upcomingDueDates`, which follows the backend's `NextDueDates`: ONE_OFF is due on delivery, a day past a month's end falls on its last day). An omitted discount becomes the company's, so the summary previews with it (`effectiveDiscount`). Clicking a service row opens Edit Service ([EditServiceForm](apps/web/src/components/clients/EditServiceForm.tsx), `PUT …/services/{assignmentId}` via `useCompany().updateService`): only the delivery date, discount and note change — the service is shown, not chosen (`toServiceUpdateRequest`). An omitted discount becomes the company's, so Edit shows the stored one (even 0); an omitted note **clears** the stored one. Delete Service (`DELETE …/services/{assignmentId}` via `useCompany().deleteService`, which also refreshes the catalog's usage counts) is in the Edit Service footer and a trash icon per row of [CompanyServicesTable](apps/web/src/components/clients/CompanyServicesTable.tsx), whose cell stops click propagation like CompaniesTable's. Add and Edit are thin wrappers over [ServiceAssignmentForm](apps/web/src/components/clients/ServiceAssignmentForm.tsx). Rules, mapping and copy in [assignments.ts](packages/schemas/src/assignments.ts). Company endpoints are under the generated `client-companies` module.
- `GET /clients` takes an optional `managerId`, unused: the list filters by manager in memory.
- Deleting a manager who still has clients returns 409; the delete dialog shows the backend's message.
- The backend's springdoc output puts an invalid `in` on the HTTP bearer security scheme; [fetch-spec.mjs](packages/api/scripts/fetch-spec.mjs) strips it (with a warning) so orval's validation passes. It also coerces string `default`s on number fields (BigDecimal `defaultValue = "18.00"`) to numbers, which orval otherwise turns into a type error. Remove that block once the backend is fixed.

## Project coding rules

- **Use [Lucide](https://lucide.dev) icons** (`lucide-react` on web, `lucide-react-native` on mobile) — no hand-rolled inline `<svg>` icons. Reuse [Spinner](apps/web/src/components/Spinner.tsx) on web / `ActivityIndicator` on mobile for loading states.
- **Web: use [shadcn/ui](https://ui.shadcn.com) components** (new-york style) where applicable rather than bespoke equivalents. Add primitives with `npx shadcn@latest add <name>` from `apps/web` — then check the generated `cn` import is `@/lib/utils`.
- **Mobile: build on the `src/components/ui/` kit** with NativeWind classes; use the semantic token classes, and `useThemeColors()` only for props that need a raw colour (icon `color`, `placeholderTextColor`, `Switch` tracks).
- **Every screen must work in both themes.** Prefer the semantic tokens (`bg-card`, `text-muted-foreground`, `border-border`, `text-destructive`, `text-success`) — they switch on their own in both apps. Where a palette colour is genuinely needed, pair it with a `dark:` variant (web). On web the theme is a `dark` class on `<html>`, set by [ThemeProvider](apps/web/src/theme/ThemeProvider.tsx) and the no-flash script in [index.html](apps/web/index.html) — the storage key and class name are shared with [theme/constants.ts](apps/web/src/theme/constants.ts), so change them together.
- **Share before you duplicate.** Logic both apps need — API calls, screen data hooks, validation, defaults, labels, constants — belongs in `packages/`, not copied into each app. Only rendering should differ between web and mobile.
- **When repeating something more than 3 times, extract a function or use a map** instead of copy-pasting. Render repeated markup from arrays via `.map` (nav items, tabs, field definitions).
- **Keep route files lean** (`apps/web/src/pages/`, `apps/mobile/src/app/`) — they orchestrate data and composition; move sections, rows, panels and forms into `components/`.
- **Put reused constants in dedicated files** under each app's `src/utils/` (or in a package when both apps use them) rather than redeclaring literals inline.

## Change log rules

- **The change log MUST be updated** in [apps/web/src/utils/changelog.ts](apps/web/src/utils/changelog.ts) whenever user-facing work is delivered in **either** app. Add the entry at the top of `CHANGELOG` (newest first).
- **Keep it high level and simple** — a short statement of what changed for users, not an itemised list of every edit. Group related work into one highlight.
- **Every entry MUST carry a date and time including seconds**, e.g. `date: "19 Aug 2026, 19:10:42"`.
- **DO NOT change the root [version](version) file.** Version bumps happen at release time, outside this workflow — write the entry against the version being prepared and leave `version` alone.
